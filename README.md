# dsh-visual-card

English | [中文](./README.zh.md)

Visual answers for DeepSeek Harness: the model hands over a block of HTML and it renders as an **interactive window** inside the conversation — clickable, keyboard-operable, fullscreen-capable, exportable.

## What it looks like

After the tool call, a window appears below the turn's answer:

- Toolbar: title plus Fullscreen / Copy / Download
- The content area is the model's HTML, and its scripts really run (buttons, canvas, animation all work)
- Colors follow the active light/dark theme automatically

## What you can build

- Charts, color swatches, layout sketches
- Clickable demos (state toggles, paging, expanding detail)
- **Complete small games** (WASD movement, per-frame canvas animation)
- When a demo needs the keyboard, clicking into the window takes it over; keys outside keep going to the composer

## Keyboard rules

| Action | Behavior |
|---|---|
| Click into the window | The window takes the keyboard; the title bar says so |
| Press Esc | Release the keyboard, back to the composer |
| Click outside | Released automatically |
| Mouse | Always works — hover, scroll and click need no focus first |

The implementation uses an iframe. Scripts generated by the model typically listen for `keydown` on `document`; if they shared the host document, keys pressed anywhere would reach them. An iframe has its own event scope, so it only receives keys while focus is inside.

## Tool

```js
render_visual({
  title: 'Title',
  html: '<div>...</div>',
  // height is optional; omit it and the card sizes itself to its content (recommended)
})
```

**Height is automatic**: once the width is fixed, the card is as tall as its content — no fixed frame. When the content exceeds the configured cap, the card scrolls internally, so even a large card never forces you to scroll the whole conversation.

Use theme variables instead of hard-coded colors:

`--v-bg-base`, `--v-bg-layer-1/2`, `--v-border`, `--v-text`, `--v-text-dim`, `--v-brand`, `--v-success/warn/error`

## Settings

Settings → Visual:

| Item | Effect |
|---|---|
| **Height cap** | Card height follows its content; above this share of the viewport (40–100%) the card scrolls internally instead of forcing a page scroll |
| **Allow scripts** | When off, buttons, animation and games do not run — only static content renders. Scripts run inside the host page, which is the only source of risk here |
| **Turns kept per conversation** | Older turns are dropped on write (10–2000) |
| **Max cards per turn** | Beyond this many in one turn only the newest are kept (1–50) |
| **Clear history** | Deletes `cards.json`, behind a second confirmation |

Changes save immediately to `~/.dsh/visual/settings.json`.

## Storage

Cards are persisted per conversation and turn to `~/.dsh/visual/cards.json`, so they survive a restart. Retention is governed by the settings above.

Deleting the directory only loses visual history; functionality is unaffected.

## Install

```bash
pnpm add github:MCJF28/dsh-visual-card
```

Then add `dsh-visual-card` to `dsh.profile.bundles` and restart the app.

## Security

Scripts generated by the model **run inside the host page** — this is not a sandbox. That is the unavoidable cost of "clickable, can run games".

The plugin only enforces "no external resources" and performs no code review. Fine for personal use; if you point it at model output you do not trust, add a sandbox first.

## Known limits

- Cards always render **below** the turn's answer and cannot be placed mid-text: the host supports a fixed set of 19 conversation node kinds, and a plugin cannot add one
- The `turnTail` slot only renders after the turn closes, so nothing appears while the answer is still streaming
